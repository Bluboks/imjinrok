# K01 정적 분석 파일럿

## 질문과 범위

K01에서 다음 동작을 원본 바이너리만으로 복원한다.

- 시작·중간 스크립트 실행 조건
- 완성된 봉화대 검색
- K0120의 일회성 실행과 후속 효과
- 보호 영웅 손실 조건
- 승리·패배 타이머와 결과 전환

UI 배치, 대사 표시 타이밍과 애니메이션은 이 문서의 현재 범위가 아니다.

## 입력 기준

- 실행 파일: `original/imjinrok2/imjinrok2.exe`
- SHA-256: `25a95d568082478ce0f50c89c9bbb9536ef33eb6904afa62903e9d63b7a5d03e`
- 분석 상태: `추정`
- 재현 상태: `미재현`
- 구현 상태: `프로토타입`

과거 문서에 비교적 상세한 정적 해석이 있지만, 전체 함수 경계와 모든 선행 분기를 새 파이프라인으로
재검증하지 않았으므로 아직 `정적 확정`으로 올리지 않는다.

Ghidra 자동 분석은 K0120 검사 지점 `0x0048a731`과 영웅 손실 검사 지점 `0x0048a812`를 모두
`FUN_0048a5c0`(`0x0048a5c0-0x0048a878`, CFG 32개, 명령어 181개)에 포함했다. 이 경계와 전체
명령어·디컴파일 결과는 `analysis/generated/imjinrok2/seeds.json`에 재현 가능하게 저장돼 있다.
이는 포함 함수의 탐색 범위를 고정하지만 아래 역할 해석을 자동으로 확정하지는 않는다.

## 원본 자원

- `script\k0110`
- `script\k0115`
- `script\k0120`
- `stagemap\k01.map`

스크립트 파일은 원본 데이터에서 직접 파싱할 수 있다. 실행 순서와 조건은 바이너리의 캠페인 핸들러로
확인해야 한다.

## K0120 봉화대 경로

현재 확보한 정적 해석:

1. `0x0048a731`에서 일회성 플래그 `WORD [0x008438dc]`를 확인한다.
2. `0x0048a742` 부근에서 레코드 스캔을 준비한다.
3. 최대 `0x4b0`개의 레코드를 검사한다.
4. `0x00441e40` 호출 결과로 비활성·누락 레코드를 건너뛰는 것으로 해석된다.
5. `BYTE [record+1]`을 현재 플레이어 후보 `WORD [0x00bccc44]`와 비교한다.
6. `BYTE [record] == 0x34`를 요구한다.
7. `BYTE [record+0x55] == 0x64`를 요구한다.
8. 조건을 만족하면 `WORD [0x008438dc]`를 설정한다.
9. `script\k0120`을 `0x00482180`, `0x00482340` 후보 함수를 통해 처리한다.
10. 후속 경로는 좌표 `55`, `53`과 관련 인수를 사용한다.

남은 확인:

- Ghidra가 제시한 `FUN_0048a5c0` 경계와 모든 선행 guard의 수동 검토
- `0x00441e40`의 반환 의미
- 레코드 stride와 활성 상태 정의
- K0120 이후 호출의 정확한 효과
- 승리 타이머가 이 경로에서 설정되는 정확한 지점

## 보호 영웅과 패배 경로

현재 확보한 정적 해석:

- `0x0048a812` 부근에서 현재 소유자의 타입 `0x4c`을 조회한다.
- `0x0048a840` 부근에서 같은 방식으로 타입 `0x4e`을 조회한다.
- `0x00441de0` 후보 함수는 선택된 레코드의 `+0x07` word를 확인한다.
- 대상이 존재하지 않거나 살아 있지 않다고 판단되고 `DWORD [0x00843740] == 0`이면 현재 틱 후보
  `DWORD [0x00882e04]`를 패배 타이머에 기록한다.

K01 시작 레코드의 현재 매핑은 다음 이름을 제안한다.

- 타입 `0x4c`: 권율 후보
- 타입 `0x4e`: 류성룡 후보

이 이름 매핑도 원본 맵 레코드와 유닛 정의 테이블을 새 파이프라인에서 교차 확인한다.

## 공통 결과 판정

현재 확보한 정적 해석:

- Ghidra 자동 경계에서 `0x0048d6f0`은 `FUN_0048d6f0`
  (`0x0048d6f0-0x0048d73a`, CFG 7개, 명령어 31개)의 시작이다.
- `0x0048d6f0`은 승리 타이머 후보 `0x0084373c`을 읽는다.
- 현재 틱 후보 `0x00882e04`와의 차이가 `0x7d0`보다 크면 승리값 `1`을 반환하는 경로가 있다.
- 패배 타이머 후보 `0x00843740`에도 같은 지연을 적용하고 패배값 `-1`을 반환하는 경로가 있다.
- `0x0048dde0`은 `FUN_0048ddb0`
  (`0x0048ddb0-0x0048deca`, CFG 36개, 명령어 105개)에 포함되며, 결과 함수를 호출하고 0이 아닌
  결과를 후속 처리하는 코드 지점으로 추정된다.

확인해야 할 경계:

- 비교가 `>`인지 `>=`인지 모든 분기에서 재확인
- 틱 값 wraparound 처리
- 승리와 패배 타이머가 동시에 설정된 경우의 우선순위
- 결과 함수 호출 주기

## 현재 구현 참조

- `packages/shared/src/scenarios.ts`
- `packages/shared/src/scenarios.test.ts`
- `packages/simulation/src/simulation.test.ts`

현재 구현에는 `0x7d0`, 봉화대 목표와 K0120 기반 이벤트가 존재한다. 이는 분석의 독립 증거가 아니며,
정적 분석이 완료된 뒤 비교 대상으로만 사용한다.

## 재현 테스트 계획

### 봉화대

- 레코드가 없으면 K0120을 실행하지 않는다.
- 다른 소유자의 완성 봉화대는 무시한다.
- 현재 소유자의 미완성 봉화대는 무시한다.
- 현재 소유자의 타입 `0x34`, 진행도 `0x64` 레코드만 트리거한다.
- 일회성 플래그가 이미 설정되면 다시 실행하지 않는다.
- 비활성 레코드가 같은 필드 값을 가져도 무시한다.

### 패배

- 두 보호 영웅이 살아 있으면 타이머를 설정하지 않는다.
- 각 영웅의 부재 조건을 독립적으로 확인한다.
- 패배 타이머는 처음 한 번만 설정되는지 확인한다.
- `0x7d0` 직전, 같은 값, 직후의 반환을 확인한다.
- 승리·패배 타이머 동시 설정을 확인한다.

## 파일럿 완료 조건

- 관련 함수 경계와 전체 제어 흐름이 저장된다.
- 사용하는 전역과 구조체 필드가 함수 지도와 자료구조 문서에 연결된다.
- 위 테스트 벡터가 독립 참조 구현 또는 원본 함수 격리 실행으로 재현된다.
- 현재 프로젝트가 동일한 벡터를 통과한다.
- 남은 추정이 파일럿 범위의 결과에 영향을 주지 않는다.
