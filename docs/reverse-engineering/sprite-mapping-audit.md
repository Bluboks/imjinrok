# 스프라이트 매핑 감사

기준일: 2026-07-26

## 판정

현재 유닛·건물 매핑은 모두 `미확인` 또는 `추정`이다. 원본 프레임 파일이 존재한다는 사실은
확인됐지만, 프레임의 방향·행동·체력 상태를 연결하는 원본 규칙은 아직 정적 확정되지 않았다.
브리핑 `SPEECH` 초상화는 별도 정적 호출·데이터 흐름을 완결해 17개 ID를 `정적 확정`했다.

기계 생성 상세는
[`analysis/generated/sprite-mapping-audit.json`](../../analysis/generated/sprite-mapping-audit.json)에
있다. 다음 명령으로 현재 코드와 원본 자원 해시에서 재생성한다.

```bash
pnpm imjinrok:audit-sprite-mappings
```

## 감사 결과

| 대상 | 확인한 범위 | 판정 |
| --- | --- | --- |
| 엔티티 비주얼 16개 | 상태 50개, 클립 290개, 프레임 참조 1,878개 | 의미 매핑 전부 `미확인` |
| 유닛 비주얼 7개 | 방향·행동·미러링 | 하드코딩된 가정, `미확인` |
| 건물 비주얼 9개 | idle·construction·overlay | 완성·체력 단계 의미 `미확인` |
| 브리핑 초상화 17개 | `K1`~`K6`·`K10`, `J1`~`J5`, `C1`~`C5` | ID→`hero.spr` 프레임 `정적 확정` |

엔티티가 참조한 PNG가 변환 매니페스트에 없는 경우는 0개다. 이 수치는 유닛·건물 자원 변환과 경로가
끊어지지 않았다는 뜻일 뿐, 올바른 방향·행동·체력 이미지가 선택됐다는 뜻은 아니다.

## 확인된 결함과 위험

### 유닛

- 공통 방향 순서를 `s, sw, w, nw, n, ne, e, se`로 고정했다.
- 다수 유닛은 원본 다섯 방향을 `n, ne, e, se, s`로 가정하고 나머지 세 방향을 좌우 반전한다.
- 이 방향 순서와 미러링 방식에 원본 바이너리·데이터 근거가 연결돼 있지 않다.
- 일본 조총병의 `attack`은 `move`·`walk`와 완전히 같은 프레임 클립을 사용한다.

따라서 사용자가 보고한 “유닛 프레임 방향이 맞지 않음”은 현재 코드 구조로 설명된다. 개별 프레임을
눈으로 다시 배치하는 대신, 원본 상태·방향 값에서 프레임을 선택하는 테이블과 수식을 복원해야 한다.

### 건물

- 건설 프레임을 0부터 임의의 `completeFrameIndex`까지 연속 범위로 잡는다.
- idle 프레임은 그 끝 또는 별도 하드코딩 번호로 선택한다.
- 본체와 깃발·불꽃 같은 오버레이 구분도 프레임 위치로 추정했다.
- 현재 체력·최대 체력·건설 진행도에서 프레임을 선택하는 원본 경로가 없다.

따라서 정상 체력 건물에 반파 이미지가 나타날 수 있다. `idle = 완성/정상`이라는 가정을 폐기하고 체력
분기와 렌더 필드를 정적으로 확인해야 한다.

### 브리핑 초상화

기존 구현의 직접 연결은 다음과 같이 잘못돼 있었다.

| 스크립트 ID | 기존 `portrait.spr` 프레임 | 확정된 `hero.spr` 프레임 |
| --- | ---: | ---: |
| `K1` | 1 | 6 |
| `K3` | 3 | 8 |
| `K10` | 30 | 15 |
| `J1` | 75 | 4 |

원본은 `portrait.spr`를 이 경로에서 사용하지 않는다. `FUN_004a7410`이 `yfnt\hero.spr`를
로드하고, `FUN_004a8870`이 ID를 17개 포인터 표에서 찾은 뒤 `0x004c91ac`의 WORD 표를 같은
인덱스로 읽는다. 전체 표와 실패 경로는
[브리핑 초상화 매핑](mechanics/briefing-portraits.md)에 기록했다.

## 정적 복원 순서

1. EXE의 캐릭터·건물 `SPR` 포인터 테이블과 엔티티 종류 인덱스를 교차 확인한다.
2. `0x0041d470`, `0x0041d560` 후보 함수와 복원된 점프 테이블이 실제 애니메이션
   상태→프레임 경로인지 호출자부터 판별한다.
3. 호출자에서 방향 필드와 행동 필드의 생성·갱신 경로를 복원한다.
4. 건물 렌더 경로에서 건설 진행도와 체력 단계가 읽히는 분기를 찾는다.
5. 완료: `SPEECH` 레코드 소비자부터 `hero.spr` 프레임 주소 계산까지 연결한다.
6. 원본 입력 값과 기대 프레임을 담은 독립 테스트 벡터를 만든다.
7. 벡터가 확정된 항목만 `themes.ts`와 브리핑 매핑에 이식한다.

상세 작업 규칙은
[스프라이트·애니메이션 매핑 지침](../agent-guides/sprite-animation-mapping.md)을 따른다.

## 이번 정적 분석에서 확보한 시작점

- `0x0041d485`와 `0x0041d579`의 간접 분기는 Ghidra가 각각 80개 case의 점프 테이블로 복원했다.
- 두 함수는 객체 `+0x1e6`의 16비트 값을 분기 키로 읽고, `+0x0a`, `+0x0c`, `+0x1b5`를 쓴다.
- 해당 필드가 프레임·방향·표시 좌표 중 무엇인지와 case 값의 의미는 아직 `추정`이다.
- 두 함수의 공통 호출자 `0x0041d210`을 새 seed로 추가했다.
- `0x00482590`은 `SPEECH`를 포함한 11개 스크립트 명령 이름을 비교해 0부터 10까지의 명령 번호를
  반환한다.
- `0x00482860`의 case 0이 `SPEECH` 레코드를 만든다. 네 인수를 읽어 첫 문자열을 보존하고, 세 번째
  인수로 `script\\eft\\%s.YAV` 경로를 만들며, 네 번째 문자열을 복사한 뒤 `0x882`바이트 레코드를
  큐에 넣는다.
- `FUN_004824c0`과 `FUN_004830f0`은 종류 0 레코드를 소비해 인물 ID, 표시 슬롯, 음성 경로와
  대사를 `FUN_004a7b10`에 전달한다.
- `FUN_004a7690`은 `FUN_004a8870`의 ID 조회 결과로 `0x004c91ac`의 17개 WORD 프레임 표를
  읽고, `hero.spr` 오프셋 표와 데이터 베이스로 최종 프레임 주소를 계산한다.
- 정적 결과는
  `K1→6`, `K2→11`, `K3→8`, `K4→9`, `K5→7`, `J1→4`, `J2→2`, `J3→3`,
  `J4→1`, `J5→0`, `C1→5`, `C2→14`, `C3→13`, `C4→10`, `C5→12`,
  `K10→15`, `K6→17`이다.
- ID 불일치 시 조회 함수는 `-1`을 반환한다. 포팅 구현은 미등록 ID의 초상화를 표시하지 않는다.

이 결과는 초상화에만 원작 일치 근거로 사용할 수 있다. 유닛 방향·행동과 건물 상태 프레임은 계속
`미확인`이다.
