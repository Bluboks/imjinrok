Static interpretation of the current xrefs:

- The `YSELECTSTAGE`/`selectstageborder` block around `0x004aafa0` checks state fields, resolves the
  `YSELECTSTAGE` control id, loads `yfnt\selectstageborder.spr`, and binds the resource into the UI path. Recover
  its surrounding arguments before tuning stage-selection dialog placement.

  paths to recover button counts, ids, and placement fields before matching modal layout visually.

- The title-stage sprite xrefs at `0x0043e99d` and `0x0043e933` identify the original country/stage title resources
  used by the menu flow. They should anchor menu art identity, not replace control geometry analysis.

Current working interpretation:

- `0x00442dd0` is repeatedly reached immediately after pushing a UI sprite path and a resource/cache pointer
  candidate. Treat it as the primary resource-load/bind call candidate.
- `0x004434a0` is repeatedly reached after passing a stack buffer and an object field pointer. Treat it as a control
  construction or copy/bind candidate until VM tracing confirms the structure layout.
- `0x0044b040` is reached from diagnostics and missing-control paths with strings such as `YMAP000 [%d]` and
  `YOKCANCEL [%s]`. Treat it as a diagnostic/assert/logging path, not as a layout constructor.
- The mouse-interface stack constants `0x119`, `0x185`, `0x120`, and `0x1c2` are candidate coordinate or extent
  values. Do not apply them to the client HUD until a runtime trace identifies the callee argument structure.
- UI runtime capture is still unproven. The menu-time attach run
  `codex-imjinrok-ui-menuprobe-20260602-1114` reached the main menu and attached x32dbg, but command-box automation did
  not produce even the after-setup PE-header proof file, so it cannot be used as call-site non-hit evidence. Treat
