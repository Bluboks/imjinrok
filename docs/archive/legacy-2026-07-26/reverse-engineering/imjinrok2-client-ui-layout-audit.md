# Imjinrok 2 Client UI Layout Audit

> Archived on 2026-07-26. This audit is retained as historical context and is not an authoritative parity report.

## Purpose

This audit marks current client UI layout surfaces that are implemented with client-side responsive formulas or local
design choices. These values may be useful MVP ergonomics, but they are not original-game layout parity until backed by
static/dynamic evidence from the original executable.

Generate the current audit with:

```sh
node tools/imjinrok/extract-client-ui-layout-audit.mjs
node tools/imjinrok/extract-client-ui-layout-audit.mjs --json
```

Regression coverage is in `tools/imjinrok/client-ui-layout-audit.test.mjs`.

## Audited Values

### HUD Shell

Current implementation uses:

- HUD height: `Phaser.Math.Clamp(this.scale.height * 0.26, 178, 220)`
- minimap width: `Phaser.Math.Clamp(width * 0.22, 190, 280)`
- action area width: `Phaser.Math.Clamp(width * 0.28, 292, 360)`
- shell frame: `fillRoundedRect(10, hudTop + 8, width - 20, hudHeight - 16, 18)`

Do not treat these as original layout constants. The nearest current original evidence is the mouse-interface static
probes in `docs/reverse-engineering/imjinrok2-ui-layout-evidence.md`, especially stack constants `0x119`, `0x185`,
`0x120`, and `0x1c2`, which still require runtime structure tracing.

### Minimap

Current implementation uses:

- diamond width: `Math.min(width - 36, (height - 54) * 1.55)`
- diamond height: `Math.min(height - 54, diamondWidth * 0.58)`
- vertical anchor: `y + 48 + diamondHeight / 2`

These formulas are client-side fit rules. Recover the original minimap/control rectangle and projection rule from
runtime draw or hit-test paths before claiming parity.

### Action Grid

Current implementation uses:

- `4` columns and `3` rows
- `8` px gap
- `x + 14` and `y + 46` content offsets
- slot width derived from `(width - 28 - gap * (columns - 1)) / columns`

This is a playable command grid, not proven original command-panel geometry. Original command slot count, ordering,
icon binding, and hit rectangles still need binary/runtime evidence.

### Selection Panel

Current implementation uses:

- portrait size: `Phaser.Math.Clamp(height - 82, 72, 106)`
- portrait position: `x + 20`, `y + 50`
- health-bar width: `Math.max(120, width - (textX - x) - 24)`
- group chip size: `Phaser.Math.Clamp((width - 54) / 8, 30, 44)`

These are local UI decisions. Trace original selected-unit panel records before using them as parity targets.

### Gameplay Selection Hitbox

Current implementation uses:

- horizontal half-width: `radius * 1.6 * zoom + padding`
- top extent: `radius * zoom + padding`
- bottom extent: `radius * 1.3 * zoom + padding`
- the same responsive HUD height clamp used by `UIScene`

Original unit hit-test bounds should be recovered from runtime selection and draw paths, not inferred from the client
render radius or visual feel.

### Campaign Dialogue

Current implementation uses:

- dialogue panel width from `Phaser.Math.Clamp(width * 0.72, compact ? 320 : 560, 920)`
- rounded panel rectangles with radius `8`
- dynamic text size threshold around line length `110`

This remains an MVP overlay. Original campaign briefing/dialogue UI needs resource/control evidence before layout parity
claims.
